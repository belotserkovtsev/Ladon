# Probe API

← [README](../README.md) · [конфигурация](configuration.md) · [методология](methodology.md)

Это контракт, по которому ладон в режиме `exit-compare` разговаривает с внешней
точкой проверки. Сам контракт небольшой и зафиксирован. Как устроена точка
внутри, дело твоё: сырой TCP, обычный HTTP-запрос, выход через мобильный модем,
headless-браузер. Важно лишь соблюдать формат запроса и ответа.

Готовая реализация на Go лежит в [`probe-server/ladon/`](../probe-server/ladon/).

## Когда ладон зовёт внешнюю точку

Локальная проба идёт всегда. Внешнюю ладон зовёт только на фоновой перепроверке
и только после того, как локальная сказала «отказ». Это единственный случай,
когда внешний ответ может что-то изменить: если локально домен открывается,
туннель не нужен и спрашивать вторую точку незачем. Заодно это самый щадящий
режим для твоего сервера. Быстрая проба «на лету» внешнюю точку не дёргает
никогда: там бюджет в доли секунды.

## Запрос

```
POST <url> HTTP/1.1
Content-Type: application/json
Authorization: <значение>     ; только если настроено
```

Адрес берётся из `probe.remote.url` в конфиге ладона. Подходят и `http://`, и
`https://`; для боевого режима лучше TLS или закрытая доверенная сеть.

```json
{
  "domain": "instagram.com",
  "ips": ["157.240.20.174"],
  "port": 443,
  "sni": "instagram.com"
}
```

| поле | тип | обязательно | смысл |
|---|---|---|---|
| `domain` | string | да | домен, который запросил клиент |
| `ips`    | string[] | нет | адреса, которые клиент получил из DNS. Если они переданы, бей по ним напрямую и свой DNS не делай: так «вид» внешней точки совпадёт с тем, что видит клиент на CDN с привязкой к региону |
| `port`   | int | да | целевой порт, обычно `443` |
| `sni`    | string | да | имя сайта для TLS-рукопожатия, обычно равно `domain` |

## Ответ

```json
{
  "dns_ok": true,
  "tcp_ok": true,
  "tls_ok": true,
  "tls12_ok": null,
  "tls13_ok": true,
  "http_ok": false,
  "resolved_ips": ["157.240.20.174"],
  "reason": "http_cutoff: read tcp ... use of closed network connection",
  "code": "http_cutoff",
  "latency_ms": 1207
}
```

| поле | тип | обязательно | смысл |
|---|---|---|---|
| `dns_ok` | bool | нет | удалось получить адреса. Если в запросе пришли `ips`, верни просто `true` |
| `tcp_ok` | bool | нет | TCP-соединение прошло |
| `tls_ok` | bool | нет | TLS-рукопожатие прошло (сертификат не проверяем, важна лишь достижимость) |
| `tls12_ok` | bool/null | нет | результат повторной попытки только по TLS 1.2: `true` прошла, `false` упала, `null` не пробовали (1.3 уже прошёл) |
| `tls13_ok` | bool/null | нет | результат первой попытки. `false` вместе с `tls12_ok=true`, скорее всего, DPI на TLS 1.3 |
| `http_ok` | bool/null | нет | удалось ли дочитать HTTP-ответ: `true` прочитан целиком, `false` поток оборвался, `null` стадию не запускали |
| `resolved_ips` | string[] | нет | адреса, по которым точка реально стучалась. Если поля нет, ладон считает, что это были адреса из `ips` |
| `reason` | string | нет | текст причины отказа. Рекомендуемый вид: `<код>: <сырая ошибка>`, например `tcp_timeout: i/o timeout`. Попадает в логи и в базу |
| `code` | string | нет | стабильный код причины (дублирует префикс `reason`). Допустимые значения: те же коды отказа, что и у локальной пробы (`tcp_refused`, `tls_alert`, `http_cutoff` и т. д.; полный список в [методологии](methodology.md#все-коды-отказа)). Если не выставлен, ладон попробует вытащить код из `reason` |
| `latency_ms` | int | нет | сколько заняла проба. Если `0`, ладон подставит свой замер |

Статус `200` значит «проба прошла корректно, смотри тело ответа». Любой не-`200`
ладон считает транспортной ошибкой: для него это «мнения нет», а не «домен
заблокирован».

### Старые серверы

Поля `tls12_ok`, `tls13_ok`, `http_ok` и `code` необязательны. Сервер, который
присылает только `{dns_ok, tcp_ok, tls_ok, reason}`, продолжает работать: ладон
вытащит код из `reason`, а HTTP-стадию просто не учтёт в решении.

## Как ладон сводит два мнения

`local`: локальная проба с твоего шлюза (идёт всегда). `remote`: твоя внешняя
точка (идёт только если локальная упала).

| local | remote | итог | почему |
|---|---|---|---|
| прошла | не вызывается | напрямую | прямой путь работает, туннель не нужен |
| отказ | прошла | **в туннель** | снаружи домен живой, значит режут именно у тебя |
| отказ | тоже отказ | напрямую | не работает с обеих точек, значит дело в сервере, а не в пути |
| отказ | недоступна | **в туннель** | мнения нет, остаётся локальный вердикт |

«Прошла» и «отказ» здесь это итог локальной пробы целиком, включая HTTP. Если
рукопожатие прошло (`tls_ok=true`), а ответ оборвался (`http_ok=false`), проба
считается отказом: это и есть блокировка на уровне приложения, как у LinkedIn и
Instagram.

Последняя строка важнее всего: недоступность твоей внешней точки ладон **никогда**
не принимает за «снаружи тоже не работает». Иначе её сбой тихо снимал бы туннель
со всех реально заблокированных доменов. В базу пишутся обе причины сразу, вида
`local:<причина>|remote:<причина>`, чтобы при разборе видеть оба сигнала.
Например: `local:tcp_timeout: i/o timeout|remote:ok:ok`.

## Самый простой сервер

Чтобы показать, что реализация не обязана быть сложной, вот заглушка на bash,
которая на всё отвечает «отказ»:

```bash
#!/bin/bash
# Слушает :8080, всё валит (демо).
while true; do
  printf 'HTTP/1.1 200 OK\r\nContent-Type: application/json\r\nContent-Length: 62\r\n\r\n{"dns_ok":false,"tcp_ok":false,"tls_ok":false,"reason":"stub"}' | nc -l -p 8080 -q 1
done
```

Версия на Go лежит в `probe-server/ladon/`. Она проходит ровно те же стадии, что
и локальная проба (DNS → TCP → TLS → HTTP), поэтому расхождение между точками
означает разницу сетевого пути, а не разную логику проверки.

## Безопасность

- Если сервер торчит в открытую сеть, **обязательно** включи `auth_header` и
  `auth_value` в конфиге ладона и проверяй их на своей стороне. Без этого пробы
  твоими руками сможет гонять кто угодно.
- Для связи между серверами лучше TLS и токен в `Authorization`.
- Если сервер в закрытой сети за firewall, можно обойтись без проверки токена,
  но тогда убедись, что сеть и правда изолирована.

## Чего в контракте нет

- Нет пакетных запросов: один запрос обрабатывает один домен.
- Нет потоковой передачи и long-poll, обычный запрос-ответ.
- Нет объединения нескольких точек: если их несколько, сшивай их сам внутри
  сервера и отдавай ладону один ответ.

Для текущей версии этого достаточно. Пакетные запросы и несколько точек можно
будет добавить позже без поломки контракта.
