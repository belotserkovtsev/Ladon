# Ладон в контейнере

← [README](../README.md) · [установка](install.md) · [конфигурация](configuration.md) · [методология](methodology.md)

Списки адресов живут внутри сетевого неймспейса. Контейнер, который только
наполняет их, вынужден занимать неймспейс хоста, и тогда изолировать нечего:
списки и правила всё равно остаются хостовыми. Этот образ вместо этого несёт
резолвер и пропускает трафик сквозь себя, так что решение принимается в том же
неймспейсе, через который идут пакеты. На хосте не появляется ничего.

Отсюда единственное требование: **трафик должен идти через контейнер**.

Это десктопная история. На шлюзе ладона правильнее ставить службой (см.
[установку](install.md)): там уже есть и резолвер, и правила. К тому же docker
на шлюзе часто настраивают так, чтобы он не трогал файрвол (`"iptables": false`
в `daemon.json`), а с такой настройкой контейнер останется без сети.

## Запуск

```bash
docker compose -f release/docker/docker-compose.yml up -d
docker exec -it ladon /opt/ladon/ladon doctor
```

Либо через установщик, он спросит и сам всё сделает:

```bash
curl -fsSL https://github.com/belotserkovtsev/ladon/releases/latest/download/install.sh \
  | sudo LADON_MODE=docker sh
```

`doctor`, `status` и `why <домен>` работают в контейнере так же, как на хосте:
образ пробрасывает аргументы прямо в CLI. Полноэкранный вывод требует `-it`.

Конфиг необязателен. Без `/etc/ladon/config.yaml` контейнер поднимается на
значениях по умолчанию и пишет об этом первой строкой лога.

> Пока через контейнер не прошёл ни один запрос, docker показывает его
> `unhealthy`, и это честно: последний шаг ещё не сделан, ладону не на чем
> работать. После первого же резолва статус меняется на `healthy`. Замечания
> вроде «systemctl не найден» на здоровье не влияют, systemd в контейнере и не
> должно быть.

## Что нужно на хосте

Ничего из того, что нужно установке службой: ни списков, ни правил, ни настройки
резолвера. Всё это внутри образа. Нужен только маршрут в контейнер.

**Своя машина.** Отдать контейнеру DNS и завернуть в него трафик:

```bash
# резолвим через него
echo "nameserver 172.30.0.2" | sudo tee /etc/resolv.conf
# и отправляем в него то, что он отберёт
sudo ip route add default via 172.30.0.2 metric 50
```

Обе команды меняют машину и сами по себе не откатываются, поэтому прежде чем
выполнять:

- `tee /etc/resolv.conf` перезаписывает файл целиком. Сохрани прежний
  (`sudo cp /etc/resolv.conf /etc/resolv.conf.bak`). На системах с
  systemd-resolved или NetworkManager файл к тому же принадлежит им и вернётся
  к своему виду при следующем изменении сети. Там правильнее прописать DNS в
  самом менеджере.
- Маршрут по умолчанию через контейнер значит, что упавший контейнер уносит
  сеть с собой. `metric 50` должен быть меньше метрики существующего маршрута,
  иначе он просто не будет использоваться. Посмотри `ip route` перед
  добавлением.

Откат:

```bash
sudo ip route del default via 172.30.0.2 metric 50
sudo cp /etc/resolv.conf.bak /etc/resolv.conf
```

`uninstall.sh` снимает контейнер, его сеть и (с `--purge`) том с базой. Эти две
строки он вернуть не может, они твои.

**Другие устройства.** Указать контейнер как DNS и шлюз, по DHCP или руками.

**Другие контейнеры.** Прицепить к его сети, и они получают сплит целиком:

```yaml
services:
  something:
    network_mode: "container:ladon"
```

## Куда уходит отобранный трафик

`LADON_EGRESS_GW` — адрес маршрутизатора, у которого уже есть туннель. Тогда
контейнеру свой туннель не нужен: он решает, что заворачивать, а несёт это
роутер.

Без этой переменной отобранное уходит обычным путём. Механику это проверяет,
но про туннель не говорит ничего.

## Чем отличается от установки службой

Изоляция здесь настоящая: списки и правила внутри, на хосте их нет, и снести их
с хоста нельзя, потому что их там и не было.

Первое соединение не теряется. Резолвер стартует после того, как движок записал
ему список доменов, поэтому адрес попадает в список, пока пишется ответ, то есть
раньше первого пакета клиента. Перезапускать при этом нечего.

Права минимальные: `NET_ADMIN` и включённый форвардинг. `privileged` не нужен,
файрвол хоста не затрагивается.
